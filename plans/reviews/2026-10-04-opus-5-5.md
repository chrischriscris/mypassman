# Independent design review: Claude Opus 5.5

2026-10-04. Requested by the maintainer and run through `claude -p` with
`--model claude-opus-5-5 --effort high`. The response metadata confirms
`claude-opus-5-5`. The maintainer explicitly approved sending the full product
brief and architecture proposal through the existing team Claude account.

Scope: the two planning documents as they stood before this review's
clarifications. Tools were disabled. Claude did not inspect source code,
run tests, verify current platform capabilities, or perform a security audit.
Its recommendations are advisory and do not approve a protocol or a rewrite.

## Disposition

The [current proposal](../ARCHITECTURE-PROPOSAL.md) incorporates these points:

- Rank format and protocol decisions ahead of UI toolkit selection. Specify
  revision ancestry, authorization, key envelopes, recovery, and checkpoints
  before designing replacement durable storage.
- Add explicit compatibility behavior between differently updated clients.
  Preserve unknown content where safe; refuse unsupported writes rather than
  silently lose fields or ignore unknown security semantics.
- Clarify that the first usable increment ships one hosting path. Cloudflare
  remains the proposed first deployment; a second production adapter is deferred.
- Start with a small two-device state-transition experiment, followed by
  representative platform integration and resource measurements.

Qualifications to the review:

- Two revisions sharing an immediate parent are only one conflict case.
  Divergent branches can each contain several edits; ancestry and concurrent
  delete/edit behavior need a complete rule. No log format is selected here.
- Device authorization is foundational, but future migration is not inevitable
  merely because an initial release exposes only personal vaults. The actual
  data and authority model determines compatibility.
- The original proposal already deferred exact protocols and recommended
  Cloudflare first. Its discussion of two eventual adapters did not explicitly
  require shipping both immediately; the wording is now clearer.
- An installed extension separates client delivery from the self-hosted relay,
  but store distribution does not eliminate compromised updates or all code
  delivery risks. Extension-first remains a sequencing suggestion, not a
  selected release order or a security guarantee.
- Known rollback detection depends on a previously trusted checkpoint. Removal
  affects future authorized activity as clients learn it; it cannot erase
  secrets already obtained or instantly inform offline devices.
- A minimum attachment limit is needed for the first supported deployment even
  if broader quotas and retention policies are decided later.

No source code, normative protocol, or existing vault was changed for this review.

# Architecture review: mypassman proposal

## 1. Overall assessment

The two documents state the constraints well and are honest about risks. They are not yet an architecture. Nearly every choice is marked "validate" or "remains open," and all carry equal weight. A few open items gate everything else: the revision/history model, the principal/key model, the item format, and the first host. They determine the local schema, the relay API, and whether the first increment's completion test can be written. Other items, such as the Windows/Linux toolkit, web framework, TUI and SSO unlock, can genuinely wait. The main correction is to rank the open decisions, not to add analysis.

Scope is the largest threat to simplicity: four GUI families, CLI, TUI, Raycast, two hosts and two storage backends. Sequencing is the right answer, but a few places quietly build for breadth early.

**What the design gets right, and should keep:**
- Local-first behavior with "saved on this device" kept distinct from "synced."
- Consolidating state into one SQLite transaction, with explicit persisted stages wherever work crosses non-transactional boundaries.
- A portable core with no I/O inside it.
- Separate permissions to decrypt, write and administer, including calling out `KeyBundle`.
- SSO treated as identity verification, not decryption.
- Candor about rollback and freshness limits, and about trusted delivery of web code.
- No destructive compaction at first.
- Relay-first sync, dropping folder sync.
- Importing old vaults into a new copy rather than overwriting.
- Chunked, separately stored attachments.
- Measuring before setting budgets.

## 2. Most consequential concerns

### 1. The revision/history model is the missing foundation

- **The claim:** The proposal says "Exact ordering and conflict representation must be specified" and "The exact history protocol remains open." Yet the first increment must "resolve a concurrent edit… reject tampering and known rollback."
- **Why it matters:** The local schema, relay API, idempotent replay, conflict detection, rollback detection and backup consistency all derive from this model. Building persistence before deciding it repeats the problem that made the current persistence a redesign candidate.
- **Smallest correction:** Write a one-page state model before any code. It should define:
  - What a revision is: identifiers, parent revision(s), authoring device, signature.
  - What role the server's ordering plays. I suggest a transport cursor only, never trusted.
  - How a conflict is detected. I suggest two revisions sharing a parent.
  - What a rollback checkpoint is.

  One simple candidate to adopt or reject with a stated reason: a per-vault append-only log of signed item revisions with parent pointers.

### 2. Device enrollment is already the membership problem (a sequencing contradiction)

- **The claim:** The key-distribution and membership protocols are listed as unresolved, and "Organization UI and SSO can ship later." But the first increment requires pairing, lost-device handling and recovery.
- **Why it matters:** A personal vault on two devices already has multiple writers whose authority must be verified. Losing a device means revoking a writer and rotating keys, which is the same operation as removing a member. A device-only scheme in v1 would force a second format and a migration once sharing arrives.
- **Smallest correction:** Define one principal model now and use it for devices in v1, even though only the owner exercises it. It should cover:
  - Persons and devices.
  - Vault key envelopes.
  - Writer authorization.
  - Removal plus rotation.
  - The recovery secret's place in the model.

  Ship no sharing UI. Get the model reviewed before the first durable format exists.

### 3. Two host adapters from the start (contradiction)

- **The claim:** "A shared Rust relay rules library with two small host adapters" conflicts with the proposal's own rule: "Build one complete path before adding deployment modes."
- **Why it matters:** Durable Objects and SQLite have different transaction models. Supporting both pulls the relay toward a storage abstraction before the protocol is stable. Attachment storage is also undecided for both hosts.
- **Smallest correction:**
  - Use one host for the first increment.
  - Keep relay rules as plain functions over a request plus the current vault state, so a second adapter stays possible later.
  - Decide now that attachment content lives outside the relay's transactional store, because that fixes the upload-then-reference ordering.

  **Mild dissent:** I'd start with the native binary because it is easier to test and debug locally. Alongside it, run a Cloudflare spike with one real operation plus one attachment upload to check fit within free-tier limits. If Cloudflare is where the maintainer will actually deploy, reverse the order, but don't build both.

### 4. Browser clients bundle two hard problems (risk, acknowledged but unresolved)

- **The claim:** The proposal has a web vault on Rust/Wasm with an IndexedDB adapter "meeting equivalent observable transaction behavior," and it notes the trusted-delivery problem.
- **Why it matters:**
  - **Trusted delivery:** If the self-hosted service also serves the web vault, that host can capture secrets at unlock. For the default self-host setup, that undercuts the brief's "relay never receives decryption keys" in practice.
  - **Duplicated storage:** A second storage implementation duplicates the most correctness-sensitive layer.
- **Smallest correction:**
  - Make the extension, whose code is signed and delivered through browser stores, the first browser client.
  - Treat the hosted web vault as a later feature with its own threat model.
  - Define the engine's storage needs as a few operations plus one atomic batch, and run both adapters against the same test suite.
- **Open question:** Can an extension hold an unlocked session through background suspension at all?

### 5. Item-format compatibility across staggered clients is missing

- **The claim:** "Custom fields allow extension," and the item-type inventory remains open.
- **Why it matters:** App-store clients update at different times. An older client that edits an item and drops fields or types it doesn't understand produces a validly signed revision that silently loses data, and sync then spreads that loss to every device.
- **Smallest correction:** Before the first durable write:
  - Define a versioned item envelope.
  - Require every client to preserve unknown fields and types on round-trip.
  - Have clients display unknown content generically.

  The type inventory itself can stay open.

## 3. Decisions: now versus later

**Before implementation:**
- Revision, history and checkpoint model (#1).
- Principal and key-envelope model, including device revocation, rotation and the recovery secret (#2).
- Item envelope and the unknown-field rule (#5).
- First host, and where attachment content lives (#3).
- Confirm the proposal's defaults: relay-first with no folder sync, and import-to-new-copy migration.
- Password-derivation parameters and the policy for upgrading them. These are expensive to change once vaults exist, so measure first (see §4).

**Can wait:**
- Windows/Linux toolkit.
- Web framework.
- TUI and Raycast.
- SSO, including SSO-based unlock.
- Organization policies.
- History retention and compaction.
- Numeric resource budgets, to be set from the first measurements.
- Attachment size limits.
- The second host adapter.
- Choice of the second client.
- A desktop unlock helper. v1 can be single-process per device and rely on SQLite locking.

**Dissent on Windows/Linux:** The "four families" grouping is the weakest premise. GPUI and Slint both draw their own widgets. Either one must reproduce native controls, accessibility and input-method behavior on two operating systems with different conventions, and the proposal concedes as much. Don't run the GPUI-versus-Slint bake-off yet. The CLI plus the browser extension can serve those platforms meanwhile. When the evaluation does happen, make screen-reader and IME behavior a pass/fail gate, not one item in a list.

## 4. Smallest useful first experiment

The proposal starts with a macOS development client plus mobile and browser compatibility experiments. I'd put a headless test first, because no UI or language bridge reduces the risk in #1 and #2.

**Headless two-device test.** Use the core crate with no UI dependencies, two device instances with separate SQLite files, and one local relay. Script these steps:
1. Create a vault.
2. Enroll device B.
3. Edit the same item offline on both devices.
4. Sync, and confirm both revisions are retained as a visible conflict.
5. Kill a sync mid-batch and replay it; confirm the result is identical.
6. Have the relay serve an older state; confirm it is rejected.
7. Remove device B; confirm the key rotates.

**Completion test:** The tests pass, and the maintainer can explain each state transition from the state-model document without reading an agent transcript. Record clean-build time and the time to edit one function and rerun its tests.

**Small parallel spike:** Measure unlock time for the chosen password-derivation function on the lowest-end target phone (through UniFFI) and in Wasm inside an extension background context. Those two numbers bound the unlock parameters, and the proposal correctly treats unlock cost as a separate budget.
