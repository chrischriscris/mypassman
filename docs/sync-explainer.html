How a password manager syncs between your devices through a server that can verify but never read — a guided tour of the pieces we just built.

the itch

Two laptops. One vault.
A server in between.

You add a login on your work machine. Tonight, on the couch machine, it's just… there. The naive way is a cloud that holds your database. But then the cloud holds your database.

✗ trust-based

Server stores your vault, encrypted or not — a breach, an insider, a subpoena, and the question is always "how much did they get?"

✓ zero-knowledge

Server stores only ciphertext it can verify — who wrote it, that it wasn't forged, that it fits the chain — and can never read.

mypassman's sync is the second kind. The trick that makes it work: every change is already a signed, encrypted frame. Sync just moves frames.

the shape

A vault is a folder,
not a file.

~/.mypassman/vault/
├── MANIFEST ← who owns this, who's allowed in
├── ops/
│   ├── 7fd5aa1f….log ← laptop A's changes
│   └── 1a25c173….log ← laptop B's changes
└── snapshots/ (compaction, later)

One append-only log per device. Nobody ever writes to anyone else's — so two devices can edit offline with zero coordination, then exchange logs and converge.

Sync is just: give the server my new lines, take their new lines.

Device signing keys live outside the vault dir (~/Library/…/mypassman/devices/) — they never travel.

a signed, sealed frame.

The signature covers seq · nonce · ciphertext — verifiable without the key. Inside the ciphertext: the item, and the hash of the previous op — the chain link.

integrity

Each op locks onto the last.

Inside every ciphertext sits prev_op_hash. Cut the log, reorder it, swap an op — the chain breaks and the vault refuses, loudly. Each device's chain is its own seq space: A counts 1,2,3… and so does B.

DEVICE A'S LOG
seq 1prev 0x000000
→
seq 2prev 9f2e1a
→
seq 3prev 41c8d0
→
seq 4prev b77e33 · head
DEVICE B'S LOG — independent
seq 1prev 0x000000
→
seq 2prev 5aa1f9 · head

When both logs live in one vault, merge is per-record, last-writer-wins by hybrid clock — every device that sees the same ops lands on the same state, in any order.

the relay

syncd: a suspicious bouncer
for ciphertext.

A Cloudflare Worker routes /v/<vault>/… to a Durable Object — a tiny single-threaded actor with its own SQLite, one per vault. Free-tier self-hostable.

it enforces
  • op signature valid for that device (from the manifest)
  • seq continues the chain — no gaps, no forks
  • manifest swap is compare-and-swap on sha256
  • epochs never go backwards
it can't
  • read a single byte of an item — no key, ever
  • add a device — that needs the owner's signature
  • forge ops — a write token only extends its own chain
tokens (stored as sha256): admin — bootstrap machine only, approves devices · write — append ops, bound to one device · read — fetch manifest/ops/state

The one idea that matters

The server keeps a pending queue — but approval isn't a row there. Approval is A re-signing the manifest with B inside it.

When B calls finish, the server looks at the manifest — a thing it cannot forge — and only then mints B's tokens. A stolen invite code buys you a queue position and nothing else.

live merge

The daemon notices
what sync dropped off.

Your unlock daemon holds the vault in memory. A sync appends foreign ops to disk while it sleeps between requests. So before answering any request — a Raycast list, a get — it:

refresh() — own log: new ops? apply. shrank/diverged? scream.
refresh_foreign() — for each other device's log:
  · reload MANIFEST if devices changed (approvals land here)
  · verify only the new suffix: sig + seq + chain
  · merge → records update by max-HLC

Net effect from the couch: sync on a cron, and the vault you open is always current — no re-unlock, no restart.

the deal

Same wire. Two views.

op seq=7 dev=A
  plaintext (after unwrap): upsert login "github" {username: me, password: •••}
  prev_op_hash: b77e33… · hlc: 1789949021500
  sig: valid under device A vk ✓
op seq=7 dev=A · 612 bytes · arrived 18:02:41Z
  nonce: 8f3a…c1
  ct:    e2 9f 41 7b 0a d3 55 18 9c 02 f7 b1 4e 88 3d 66 a0 12 …
  sig:   valid under device A vk ✓   ← all it will ever know

Metadata leaks — device ids, op counts, timing. Content doesn't. A hostile server's best moves are withholding (availability) and reordering — both detected, never silently accepted.
