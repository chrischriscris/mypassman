Two devices, one vault, and a relay that can never read either.

mypassman syncs by mailing sealed envelopes through a post office that checks every seal but can't open a single letter. This page walks through how that works, with a live two-device sync you can step through yourself.

First,

A vault is just a folder of sealed things.

There is no database. A vault is a directory with one signed index file and one append-only log per device that has ever written to it. Each log is a chain of encrypted, signed operations. Nothing in the folder is secret on its own: you could publish it and lose nothing but privacy of shape.

The things that are secret live somewhere else entirely. Your device's signing key and its sync credentials sit in your user data directory, mode 0600, never inside the vault. That split is what lets the whole folder travel through a relay, an iCloud drive, or a USB stick without carrying the authority to change itself.

Then,

One operation, as it looks on disk and on the wire.

Every change to the vault is one op: a small sealed frame appended to the writing device's log. The same bytes that sit on disk are the bytes that travel to the relay and land in the other device's copy of that log. Nothing is re-encoded along the way, so a frame is either the original or it isn't.

Hover over a part of the frame. Then flip who is looking at it.

Op frame
the signature covers seq, nonce and ciphertext
prev_op_hash hlc type record_id kind name fields (encrypted again, per record)

Two consequences follow from that layout. The signature preimage is the seq, the nonce and the ciphertext, prefixed by a fixed context string, so anyone can verify the frame without holding a single key. And because the hash of the previous op is sealed inside the ciphertext, only someone who can decrypt can walk the chain, while the relay still enforces that seq numbers never skip.

Sequence numbers are per device. Your laptop's op 12 and your phone's op 12 are unrelated, which is what lets both write offline without asking anyone. When the logs meet, each record keeps whichever op carries the highest hybrid logical clock, with the writing device and its seq as the tie-break. That is a total order on ops, so the merged result depends only on which ops exist, never on the order they arrived in.

About the middle lane:

The relay is a bouncer, not a librarian.

syncd exists in two interchangeable bodies behind one wire protocol. The Cloudflare version is a Worker in front of one Durable Object per vault — the zero-infra option, deployable on the free tier. The self-host option is mpm-syncd, a single Rust binary (axum + SQLite, one .db file per vault) that reuses the same verification crate as the client — so the crypto can't drift. A Docker image is about 100 MB: docker run -v data:/data -e MPM_SETUP_KEY=… -p 8787:8787 is the whole VPS story. Clients can't tell which backend they are talking to.

Each vault's state lives in one serialized context — a single-threaded Durable Object, or a per-vault mutex in the Rust version — holding a small SQLite database: the current manifest, the op frames keyed by device and seq, hashed tokens, live invite codes, and a queue of devices asking to join. Appending ops and swapping the manifest are plain transactions. There is no coordinator to build and no race to win.

It stores only what it can verify. Before an op frame is accepted the relay checks that the bearer token is bound to the device named in the URL, that the device is in the manifest's registry and still active, that the ed25519 signature verifies against that device's public key, and that the seq is exactly the head plus one. A re-push of identical bytes is silently fine. Different bytes at an existing seq is called out as equivocation and refused.

Before a manifest is replaced it checks the owner signature, that the vault id is unchanged, that the owner key itself is unchanged — owner_vk is pinned at bootstrap, so an admin token can't quietly swap in a manifest signed by a different key — that neither epoch went backwards, and that the caller's base_hash matches the sha256 of what is currently stored. That last check is a compare-and-swap: two admins racing to add devices can't overwrite each other, and the loser is told to pull and try again.

Three tokens and one key

  • admin is minted once, at bootstrap, to the machine that sets the vault up. It can replace the manifest, mint other tokens, revoke devices and issue invites.
  • write is bound to one device id. It can append to that device's log only, and it can read sync state, so a day-to-day device needs nothing else.
  • read can pull state, ops and the manifest. Nothing more.
  • SETUP_KEY is the only secret the Worker itself holds. It authorises exactly one call per vault, the bootstrap that uploads the first manifest and returns the admin token. Rotating it changes nothing for existing tokens.

Tokens are stored hashed. A leaked write token lets an attacker extend one device's chain with frames that device has already signed, which is to say, replay what the relay already has. It can't forge a frame, because the signature check needs the device's private key, and that never leaves the device.

In order:

One sync is four moves, and you never have to unlock.

Everything that crosses the wire is ciphertext or a signature, so mypassman sync reads the logs as bytes and never decrypts anything. Run it whenever. Running it twice in a row is harmless, because every move is idempotent.

Ask where everyone is

One cheap probe returns the manifest's snapshot epoch and the highest seq the relay holds for each device.

GET /v/<vault>/state → { snapshot_epoch, heads: [{device, head}] }

Pull what other devices wrote

For each foreign device whose head is past your local copy of its log, fetch frames since your count in pages of up to 256. Each frame is verified before it touches the log — seq continuity plus the device signature against the manifest registry, no unlock needed — so a hostile relay can't poison your log with bytes that only fail later. Good frames append to ops/<device>.log verbatim; a bad one aborts the sync.

GET /v/<vault>/ops?device=…&since=N&limit=256 → raw frames, x-head, x-more

Push what you wrote

Send your own frames past the relay's head for your device. If the relay holds more of your ops than you do, this device lost state, most likely a restored backup, and the client says so rather than fork the chain.

POST /v/<vault>/ops?device=<me> ← raw frames

Reconcile the manifest

Fetch the relay's manifest. Before anything is adopted, the client pins the trust anchors: the owner key must be identical (it never rotates) and the key epoch may not regress. Then epochs decide: strictly newer wins, older loses and is pushed back if you hold admin, and an equal epoch with different bytes means your local change lost a CAS race — the relay's copy wins and you're told to redo the change. Because every owner-signed write bumps the epoch, a replayed old manifest can never win.

GET /v/<vault>/manifest   PUT /v/<vault>/manifest { manifest, base_hash }
Adding a device:

Approval is a signature, not a checkbox.

A new phone has no keys and no tokens. It has to become a line in the owner-signed manifest, and only a device that can unlock the vault can write that line. The relay's job here is to carry a request and hold the door. It never decides who gets in.

Notice what the pending table is not. It is a queue of requests, so the owner can list them by name and key fingerprint. Declining just deletes a row. Approving does nothing to the table at all: it appends a device entry to the manifest, signs it with the owner key, and pushes it. The relay's only test at pair finish is whether the device now appears, active, in that signed manifest. Until it does, the answer is 409.

The invite is printed as <vault_id>.<code> because the code alone can't route: the vault id is what selects which Durable Object holds the vault. The code lives fifteen minutes, is stored hashed, and is burned the moment it is exchanged for tokens. pair invite --qr renders a terminal QR encoding an mpm://pair?server=…&invite=… deep link — on a phone, enrollment becomes scan, type the vault password, done.

Two checks keep the ceremony honest. The new device prints its vk fingerprint and pair pending shows the fingerprint of whoever actually joined — the owner compares them before signing, SSH-style, because a relay could otherwise swap the submitted key under a familiar name (it can't steal anything, the vault key never leaves, but it could wedge the enrollment). And pair finish redeems the invite only for the device that joined under it: the server requires a pending row whose key matches the one the owner just signed, so a stolen code can't mint tokens for a device that was already active.

The mirror image is pair revoke: the owner re-signs the manifest with the device's active flag cleared and a revocation horizon recorded — the seq head the relay held for it at that moment. Ops the device wrote while still trusted (seq ≤ horizon) keep merging on every replica, so a lost phone's history survives its own revocation; anything it writes after is refused on push, dropped at pull, and rejected at merge — including on the revoked device itself once it learns the new manifest. The relay burns its tokens, so its next call gets a 401. And by default the DEK itself rotates: a fresh key_epoch is minted and every wrap slot is re-wrapped under a NEW master password — necessary, because the revoked device knew the old one and could otherwise unwrap the rotated bundle. Its DEK history ends at the rotation: ops already written stay readable everywhere (you can't unread what it saw), but anything sealed at the new epoch is unreachable even if the ciphertext lands in its hands. --keep-keys skips this when secrecy isn't the point.

Meanwhile, on the same machine:

The unlocked daemon notices without being told.

On a Mac the vault is usually held open by a daemon so the app and the browser extension don't have to prompt for a password every time. Sync itself runs as a background thread inside that same daemon — every MPM_SYNC_EVERY seconds (default a few minutes) it exchanges ciphertext without ever touching the unlocked keys, since moving frames needs no decryption. A manual sync and the daemon's timer take a per-vault lockfile so they can never interleave their appends. The daemon treats the disk as the source of truth and re-checks it before every request it answers — so whatever sync pulled merges on the next request, no re-unlock.

The verification is incremental. The daemon remembers, for every foreign log, how many ops it has applied and the hash of the last one. When a log grows, it verifies only the new suffix, chaining it onto that remembered hash. If a log ever shrinks, or the suffix doesn't chain, the daemon refuses and asks to be restarted rather than guess.

It also reloads the manifest whenever foreign logs exist, because pairing and revocation arrive as a new manifest on disk. A device that was added since unlock becomes trusted. A device that was revoked keeps contributing up to its revocation horizon — the ops it wrote while trusted — and stops there. And a log that fails verification mid-file is quarantined, not fatal: the daemon applies the good prefix, warns once, and keeps serving. The reload is refused if the vault id, owner key or key epoch changed, since that would mean the DEK in memory is stale.

Finally,

Give the relay to an adversary. Try things.

Assume the Worker, the Durable Object and the account behind them are fully compromised. Pick something the attacker might attempt and see which check stops it, or, in a couple of cases, what they actually get.

Since the third: multi-epoch key bundles — pair revoke rotates the DEK (with a new master password, or it would be theater), so a revoked device can never read post-revocation ciphertext. Since the fourth: compaction — signed checkpoint ops carry the covered per-device vector plus every record's winning frame (tombstones included); replicas adopt one only after re-deriving the same winner set from their own verified replay, then drop covered log prefixes and anchor chain verification at the covered head. The relay stays oblivious (it keeps full history; sync cursors are logical seqs), and unknown op types decode inert so older clients never wedge. Still open: conflict copies, gossip vectors, restored-device handling.
